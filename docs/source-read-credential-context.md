# Source-read credential contexts

Status: main-first implementation in progress; no complete authenticated Reader or production qualification is claimed yet.

Long-running external reads need renewable credentials bound to the operation that opened them. Storage properties cannot represent that operation's authorization lifetime. On current main, Lance and Iceberg delegate storage reads to the C++ filesystem. Release 3.0 still has independent Rust-native credential providers; those require a separate adaptation after shared native support lands on main.

## Authority and ownership

The engine authenticates the initiating user and owns durable source bindings, provenance, recovery and revocation. Storage receives a runtime-only context from that trusted engine. It does not interpret usernames, durable references, catalog ACLs or arbitrary headers as authority.

A context owns immutable allowed Azure roots, a credential provider, an optional operation deadline and cancellation state. Storage generates its process-local identity. Independent contexts cannot share credential-bearing objects, even for the same table; sharing within one retained context is permitted. Credentials, callback pointers and process-local handles must never enter serialized properties, manifests or job metadata. Recovery constructs a new context through the engine's trusted authorization path.

The versioned C ABI uses opaque retained handles and explicit result-release and userdata-destruction callbacks. Source-reader construction retains the context independently of the caller's handle. Destruction waits for all native/Rust owners and callbacks to drain. Go adapters use managed runtime handles, never Go pointers retained in native memory.

## Credentials and failures

A provider receives a normalized resource URI, authorized root, read/list operation and finite request deadline. It reauthorizes the immutable engine binding at each issuance and returns an Azure SAS with account, root and expiration, or one of Denied, Expired, Transient, Cancelled and InvalidResponse. Callbacks are thread-safe and must honor their deadline. Returned credential buffers are copied before release.

Storage validates account, root, signed directory scope, permission, syntax and expiry after acquisition. Only explicit Transient failures permit bounded retry or fallback to an actually unexpired cached SAS. InvalidResponse is terminal. A provider denial invalidates the entire context. Waiting callers share their acquisition attempt's typed failure, while later independent requests can recover from non-latching failures. Credentials and issuer response bodies never appear in diagnostics.

Source-context cancellation/deadline applies to cached results and in-flight work, not only to token acquisition. An SDK caller's cancellation affects that caller; a live waiter can reacquire after a cancelled leader's callback returns. The implementation does not interrupt or detach a blocking provider callback. Existing SAS authority lasts until its actual expiry; this is not a promise of immediate issuer revocation of already issued credentials.

The native source policy runs per SDK attempt on both Blob and DataLake clients. Internally it returns Arrow statuses and shares the completed status with waiters. The SDK's response-only policy interface carries local failures in a marked, non-retryable response without dispatching a storage request; the native exception translator decodes that marker before ordinary Azure classification. This prevents SDK retries from multiplying the provider's bounded retry batch. The carrier contains only fixed error categories, never issuer text or credentials. Allocation and unexpected internal failures remain distinct from provider failures. Clones share cache state only within their retained context, partitioned by root and read/list operation. Signed URLs are restored to the unsigned request on exit. Native source status details preserve codes 117-121 through the C ABI: Denied, Expired, Transient, Cancelled and InvalidResponse. Only 119 is retryable. Main's existing permission-denied and asynchronous I/O codes remain unchanged. Rust planner errors must preserve these categories through native FileIO and the CXX return path; stringifying them is not sufficient.

## Source scope and internal writes

All metadata, manifest, data and positional-delete references must remain within immutable authorized roots. Validate authority and path-component boundaries before URI stripping or decoding. The strict parser accepts secure ABFSS and HTTPS Blob/DFS URLs. Milvus/Lance aliases require an explicit account, cloud endpoint and container binding; they do not supply authorization. Decode each object key once. Normalize encoded separators and ambiguous roots before any legacy path handling.

The context-aware filesystem entry point requires explicit Azure account/provider configuration, rejects ambient/static-key/IAM/broker alternatives, and returns canonical source identity, decoded path and filesystem together. Weak cache entries use the generated context identity plus verified account/endpoint/container. Directory SAS uses the required HNS path without the container-root ACL probe and rejects mutations. Live Azure HNS qualification is still required.

External Explore also writes an internal manifest. Source credentials apply only to source I/O. Internal manifest writes retain the engine's internal-storage identity. Failed source exploration must not write an internal manifest.

## Reader propagation and caches

Explicit context-aware Reader, Explore and file-info entry points require a live context. Unsupported formats reject them before any legacy fallback. Never put operation state on a singleton Format.

The final implementation must retain and check context through ReaderImpl, PackedRecordBatchReader, ChunkReaderImpl, column-group and lazy readers, metadata loaders, format readers, clones, streaming batches and async captures. The same applies to cached and zero-length reads. Per-context cache isolation includes filesystem state, Lance dataset/readers, metadata caches and Rust scheduler identities. Identity cannot be discarded when a factory reconstructs options. Source files and positional-delete paths must not fall through to the legacy filesystem resolver.

## Current implementation and verification gates

The native context/provider, C handle lifetime, scope parser, Azure SDK policy, context-aware filesystem and Parquet format/stream guards have been ported into this main worktree. The port adapts main's shared immutable Properties API and retains its current permission errors, async APIs and footer constants. Explore/file-info C entry points are implemented for the available context-aware formats. Reader construction and its C ABI now retain the context through chunk readers, buffered streams, deferred futures and metadata-cache resets. Column-group readers retain guarded base readers while keeping their format-specific immutable metadata caches. Lance source exploration and metadata loading use the validated source filesystem; both its process-wide Dataset cache and Rust scheduler use that filesystem's context identity. Native asynchronous metadata and fragment opening remain asynchronous. Source Lance fragment selectors are parsed strictly, including on metadata cache hits, and canonical URI escaping is preserved before entering Rust. Optional Lance memory estimation must propagate source authorization failures. The actual main native integration tests now exercise these paths with generated data and injected Azure transports. Iceberg now asks the retained native source filesystem to validate every complete URI before OpenDAL receives a decoded relative key. Its source binding retains the runtime filesystem and cannot regain authority after serialization. Source planning preserves account-bearing output URIs; native positional-delete loading compares validated canonical identities instead of stripping account endpoints. The context-aware Iceberg metadata loader reuses Parquet metadata and applies scoped deletes. ## Integration checkpoint limitations

This main-based branch is a consumable native integration checkpoint for the engine adapter, not production qualification. The external source C ABI is stable for that integration. Before an upstream feature review or rollout, validate the original-user Catalog/Milvus authorization and retry path on live Azure. Complete-Iceberg planning and adversarial Lance URI validation now have native coverage as described above; generated adversarial Lance index and deletion-file references remain additional qualification gaps; embedded data BasePaths are covered as described above. Engine recovery must reconstruct runtime authority; neither serialized options nor a cache key authorizes a read. No OBO grant or deployment change is included here.

The 79 native integration cases use actual main Rust/C++ code and Azure SDK clients with injected transports and clocks. Standalone Rust unit tests added for source identity parsing and serialization have not been executed separately. OOM/unexpected-exception translation is implemented but not fault-injected. The ordinary shared-library exports were checked; the Python/hidden-symbol build has not been separately qualified. These limits are retained so downstream integration does not mistake a native checkpoint for end-to-end approval.
